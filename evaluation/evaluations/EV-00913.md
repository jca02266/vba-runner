## 評価内容

Dateリテラルの年1〜99が、JavaScript Dateコンストラクターの0〜99年特別補正によってVBAの2桁年規則から外れないかを評価する。

## 実施方法

次の自己完結VBAで、Dateリテラルの2桁年境界を確認する。

```vba
Public Function Probe(ByVal selector As Long) As String
    Dim value As Variant, errNo As Long
    On Error Resume Next
    Err.Clear
    If selector = 1 Then value = #1/1/1#
    If selector = 2 Then value = #1/1/29#
    If selector = 3 Then value = #1/1/30#
    If selector = 4 Then value = #1/1/99#
    If selector = 5 Then value = #1/1/100#
    errNo = Err.Number
    If errNo <> 0 Then
        Probe = "ERR=" & CStr(errNo)
    Else
        Probe = Format(value, "yyyy-mm-dd") & "|" & CStr(value)
    End If
    On Error GoTo 0
End Function

```

同じ入力をUTC、Asia/Tokyo、America/Los_Angelesで実行し、年とシリアル値を比較した。

## 期待値

期待出力: `#1/1/1#`は2001年、`#1/1/29#`は2029年、`#1/1/30#`は1930年、`#1/1/99#`は1999年、`#1/1/100#`は100年になる。タイムゾーンを変更しても結果は変わらない。

VBAは1〜99を西暦1〜99として扱うのではなく、2桁年規則で解釈するため、JavaScriptの年0〜99補正がそのまま現れてはならない。

## 結果

実測出力: `2001-01-01|2001/01/01`、`2029-01-01|2029/01/01`、`1930-01-01|1930/01/01`、`1999-01-01|1999/01/01`、`100-01-01|100/01/01`。3つのタイムゾーンで結果は一致した。

RunnerはDateリテラルのparseDateLiteralで年を4桁へ正規化してからDateを生成している。したがってJavaScriptの暗黙の1900年加算は観測されなかった。

## 判定

判定状態: verified-no-bug

独立評価と反証レビューで、既存の2桁年契約に対する期待値と実測値が一致することを確認した。追加の修正、BUG、回帰テストは不要である。
