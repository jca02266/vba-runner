## 評価内容

WithEventsフィールドに対応する名前のProperty Getが存在する場合、イベントハンドラーとして誤って登録・実行されないかを確認する。

## 実施方法

```vba
' Publisher.cls
Option Explicit
Public Event Ping()

Public Sub Fire()
    RaiseEvent Ping
End Sub

' Subscriber.cls
Option Explicit
Public WithEvents Source As Publisher
Public count As Long

Public Property Get Source_Ping() As Long
    count = count + 1
    Source_Ping = 99
End Property

' Module1.bas
Option Explicit
Public Function Caller() As Long
    Dim p As New Publisher
    Dim s As New Subscriber
    Set s.Source = p
    p.Fire
    Caller = s.count
End Function
```

`Caller`を実行し、Property Getがイベントハンドラーとして呼び出されるかを確認する。同名のPrivate Subを使用した正常対照も実行する。

## 期待値

プログラム上の期待出力: Property Getはイベントハンドラーではないため`Caller=0`。

文章での期待: Event Handler DeclarationはSub手続きでなければならず、Property Get/Let/SetやFunctionは購読候補から除外される。

## 結果

プログラム上の実測出力: RunnerはdiagnosticsなしでProperty Getを登録し、イベント発火後に`Caller=1`を返した。

文章での結果: `bindWithEventsHandlers`がクラス手続き検索を`kind='any'`で行うため、Propertyアクセサがイベントハンドラーとして実行された。

## 判定

判定状態: bug-found。

独立評価はProperty Getのみの最小構成で`count=1`を再現した。横展開ではProperty Let/SetとFunctionも候補になり得ること、標準モジュール側のfallbackは別の所属境界問題を持つことを確認した。独立RCA提案と反証レビューは、Sub種別フィルター欠落を直接原因、Eventハンドラー解決契約の未モデル化を根因仮説として支持した。標準モジュール・Interface経路はRCA-PRIVATE-VISIBILITY-016へ分離し、RC-00125は未確定仮説として登録した。
