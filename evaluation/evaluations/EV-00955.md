## 評価内容

モジュールレベルのUDT変数をUDT宣言より前に記述した場合でも、UDT宣言を先に記述した場合と同じ既定値で初期化されるかを評価する。

## 実施方法

```vba
Option Explicit

Private state As StateRecord

Private Type StateRecord
    Value As Long
End Type

Public Function Probe() As String
    Dim initial As Long
    initial = state.Value
    state.Value = 42
    Probe = CStr(initial) & ":" & CStr(state.Value)
End Function
```

対照として、次のように`Private Type StateRecord`を変数宣言より前へ移動したソースも評価した。

```vba
Option Explicit

Private Type StateRecord
    Value As Long
End Type

Private state As StateRecord

Public Function Probe() As String
    Dim initial As Long
    initial = state.Value
    state.Value = 42
    Probe = CStr(initial) & ":" & CStr(state.Value)
End Function
```

さらに、同じ前後関係を`XL-251`として既存のExcel実機キューへ追加した。

## 期待値

期待出力：`Probe=0:42`。Excel実機キューでは`XL-251 FORWARD=0:42 PRIOR=0:42`。

MS-VBALの型束縛コンテキストでは、同一モジュールのUDTは宣言順によらず型名として束縛される。モジュール変数は作成時に宣言型の既定値を持つため、どちらの宣言順でも`state`は`StateRecord`として初期化され、Longメンバーの既定値0を読んだ後に42を代入して読み戻せる。独立仕様レビューでは、§5.2と§5.2.3にUDTを変数より前に置く順序制約がなく、§5.6.16.7の型束縛対象がモジュールのUDTであることを確認した。ただし、Excel実機がこの宣言順を受理するかは別途確認する。

## 結果

vba-runner実測出力：後置UDT宣言では`Run-time error '91': Object variable or With block variable not set`、前置UDT宣言では`Probe=0:42`。

Excel実機出力：`XL-251 FORWARD=0:42 PRIOR=0:42`。

Excelでは後置した場合もUDTとして初期化され、宣言順による差は発生しなかった。差分はvba-runner固有の実装差である。

## 判定

判定状態: bug-found

MS-VBAL上の期待とExcel実機の結果は一致したが、vba-runnerだけがError 91となった。後置UDT宣言を受理するExcelとの互換性バグとして確定する。
