# 真因分析手順

評価で確認した不具合は、目に見える失敗箇所（直接原因）だけを修正して
終了してはならない。直接原因を生む設計上の真因を特定し、同じ真因を持つ
別経路を調査してから、修正または妥当な制限として記録する。

## 分析の入力

- 最小再現コードと期待値の根拠（仕様、実Excelログ、または未検証仮説）
- 失敗した入口から例外発生までの呼出し・評価経路
- 横展開調査で確認した経路、除外した経路、未確認の経路
- 既存の `directCauseKey`、`causeKey`、回帰テスト、カバレッジ参照

分析担当にはこの入力だけを渡し、TODOやgit履歴から結論を誘導しない。

## 分析の順序

1. 期待値が仕様または実Excelで確定しているか確認する。仮説なら追加検証を
   先に行い、確定できない場合はバグ扱いにしない。
2. 最小再現を実行し、失敗する入口と最初に誤った状態を記録する。
3. パーサー、名前解決、評価、変換、参照寿命、エラー伝播、ディスパッチなど
   の境界を追い、直接原因を一文で表す。
4. 同じ責務を持つ全入口（通常呼出し、Member/With、組み込み・COM、動的呼出し、
   ByRef/Property、配列・スカラー）を列挙し、同じ真因の確認済み・除外・未解決を
   分ける。共通化不足は候補の一つであり、他の原因を同じ粒度で検討する。
5. 真因の確度を `confirmed` / `uncertain` とし、根拠となるソース位置とテストを
   記録する。確度が `uncertain` のまま実装修正しない。
6. 対処を、共通化、局所修正、仕様上の制限、追加調査のいずれかに決める。
   追加調査が残る場合、直接修正済みでも `rootFixStatus` は `pending` とする。

## 評価記録への反映

`evaluation/evaluations/EV-*.md` と Finding には次を別々に記録する。

- `directCauseKey`: 直ちに誤動作を起こした機構
- `causeKey`: その機構を生んだ設計・状態・境界上の真因
- `rootCauseAnalysis`: `status`, `directCause`, `designCause`, `confirmed`,
  `ruledOut`, `unresolved`, `decision`
- `directFixStatus` と `rootFixStatus`（別候補で対処するなら候補IDとコミット）

`unresolved` が残る状態で `rootFixStatus: fixed` としてはならない。未解決の
境界を新しい候補へ切り出した場合だけ、元の評価の未解決を空にし、後続候補へ
引き継いだことを記録する。

## サブエージェントの役割

評価ループは、再現後に横展開担当、次にこの手順を読む真因分析担当を別々に
起動する。真因分析担当は変更せず、上記の形式で報告する。rootは報告とソース・
テストを照合して記録を更新し、真因が確定した場合だけ別の実装タスクを起動する。
実装後は、元の再現と横展開で確認した代表経路の回帰テストを実行し、記録した
`causeKey`に対処できていることを検証する。
