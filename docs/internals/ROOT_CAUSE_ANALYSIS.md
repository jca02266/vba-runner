# 真因分析と対処タスクの手順

## 目的

目に見える失敗箇所や、最初に見つかった条件分岐を真因とみなさない。
VBAの意味上どの責務が欠け、その結果どの実装経路に同種の例外処理が増えたかを、
反証可能な仮説として段階的に特定する。

分析担当の最初の提案は必ず仮説である。別の分析担当による補足・反証を経て、
未解決の問いがなくなった場合だけ真因として確定し、対処タスクを作成する。

## 記録単位

- 評価記録は、観測した事象と直接原因を`EV-xxxxx`へ保存する。
- 真因仮説とレビュー履歴は`evaluation/root-causes/RC-xxxxx.md`へ保存する。
- 確定した真因への設計変更は`evaluation/remediations/ROOT-xxxxx.md`へ保存する。
- `causeKey`は原因の分類名であり、一意性は`RC-xxxxx`と`ROOT-xxxxx`で保証する。

評価、真因ケース、対処タスクには`procedureVersion`を記録する。現在の手順書の
バージョンは`1`である。手順が存在しなかった過去評価は`0`とし、番号や状態から
方式を推測しない。

評価候補は「何を調べるか」、真因対処タスクは「確定した設計原因をどう除去するか」を
表す。両者を同じ候補IDで代用しない。

## 入力を固定する

分析担当には次だけを渡す。TODOや無関係なgit履歴から結論を誘導しない。

1. 最小再現と、期待値を確定した仕様または実Excelログ。
2. 入口から観測された失敗までの実行経路。
3. 直接修正の差分があれば、その差分と修正前後の回帰テスト。
4. 横展開で確認済み、除外済み、未確認となった経路。
5. 関係する型・値・状態の内部表現。

期待値が仮説のままなら、製品バグの真因分析へ進まず期待値を先に検証する。

## 第1段階: 最初の真因仮説を作る

最初の分析担当はコードを変更せず、次を順番に実施する。

### 1. 最初に誤った状態を特定する

例外を投げた行や誤った出力行ではなく、正しい意味分類・値・参照・制御状態が
初めて失われた位置を探す。その状態が後段へどう伝播したかを記録する。

### 2. 直接原因を実装用語で記述する

入口、分岐条件、誤分類、欠落した変換などを一文で表す。この記述を
`directCauseKey`へ対応させる。特定の配列チェックがない、といった記述は通常ここに属する。

### 3. 責務をVBAの意味用語で言い直す

実装条件をそのまま一般化せず、VBAとして本来区別すべき概念を記述する。

- Object参照と値
- 宣言型と実行時型
- ByRefの参照と一時値
- 名前の所有スコープと親スコープ
- 評価順序と副作用
- エラー状態と通常値

JavaScriptの`typeof object`のようなホスト言語の分類は、VBAの意味分類の根拠にしない。

### 4. 欠けている不変条件または所有責務を探す

正しい状態を保証すべき層と述語を特定する。次を問い、どれか一つの例外条件を
追加するだけで終わらせない。

1. この判断を一箇所で表す定義や述語はあるか。
2. 同じ意味判断が複数の入口へ重複していないか。
3. 値の生成時に付けるべき型情報を、利用側が推測していないか。
4. 正しい責務層より後段で症状だけを補正していないか。
5. 一つの不変条件で過去の複数事象を説明できるか。

### 5. 反例集合で仮説を試す

肯定例だけでなく、隣接する否定例を列挙する。Object参照分類なら、少なくとも
`Nothing`、VBAクラス、COM/hostオブジェクト、Collection、配列、UDT、Date、Currency、
Decimal、Error、プリミティブを分類する。分類不能な値は`unresolved`へ残す。

### 6. 代替仮説を残す

同じ事象を説明できる別原因を最低一つ検討する。ソースまたはテストで除外できたものは
`alternatives`へ理由付きで記録し、除外できないものは`unresolved`へ置く。

### 7. 仮説として登録する

`RC-xxxxx.md`を`procedureVersion: 1`、`status: hypothesis`で作成し、`proposedBy`へ担当を記録する。
最初の担当者は自分の提案をレビューまたは`confirmed`にしてはならない。

## 第2段階: 独立レビューで仮説を深める

別の分析担当は先の結論を採用することから始めず、同じ入力と`RC-xxxxx.md`を読み、
次のいずれかをレビューとして追記する。

- `supplement`: 説明範囲、反例、横展開先、受入条件を追加する。
- `challenge`: 説明できない事象、誤った責務境界、未検証の前提を示す。
- `confirm`: 代替仮説を除外し、記録した真因が事象と横展開先を説明すると確認する。
- `reject`: より深い仮説または別の仮説へ置き換える。

レビューで新しい問いが出たら`status: under-review`として、最小のソース調査または
テストを行う。最初の仮説へ条件を継ぎ足すより、責務の定義を一段上げることで複数の
条件を説明できないか再検討する。

rootは、独立した`confirm`レビューがあり、`unresolved`が空で、仮説が次を満たす場合だけ
`status: confirmed`へ変更する。

1. 元の事象を説明する。
2. 横展開で確認した同種事象を同じ不変条件で説明する。
3. 除外対象が同じ真因でない理由を説明する。
4. 局所ガードではなく、責務を置くべき層を特定する。
5. 実装後に判定できる受入条件を導ける。

## 第3段階: 真因対処タスクを定義する

真因が確定するまでは`ROOT-xxxxx`を作らない。確定後、次を持つタスクを作成する。

- `rootCauseId`と`causeKey`
- 起点の評価・Finding
- 変更対象と明示的な対象外
- 観測可能な受入条件
- 元事象と横展開経路を覆うテスト
- `queued`、`in-progress`、`completed`、`blocked`、`cancelled`の状態

タスク実装は、直接修正のコミットが完了した後の別作業として行う。開始時に
`in-progress`へ変更し、共通の意味述語または不変条件を実装してから各入口を移行する。
互換性のため残す経路は`scope.exclude`に理由を記録する。

`completed`にする前に、受入条件、元の回帰、横展開回帰、型検査を確認し、実装コミットを
記録する。起点評価の`rootFixTaskId`と`rootFixCommit`を更新して初めて
`rootFixStatus: fixed`とする。

## 過去評価を参照する場合

過去の`EV-xxxxx`を参照したときは、最初に`rootCauseProcedureVersion`を確認する。

1. `0`は手順未整備時代の記録であり、本文の`confirmed`は新方式の独立レビュー済み確定とは扱わない。
2. `1`はこの文書の手順に従った記録である。`hypothesis`または`not-applicable`では
   真因が未確定・非該当のため`rootCauseId`を持たなくてよい。`confirmed`へ進める
   場合は、`rootCauseId`の`procedureVersion: 1`、独立`confirm`レビュー、空の
   `unresolved`を確認する。
3. 項目がない、または参照先のバージョンが一致しない場合は、真因確定済みとして利用せず、
   `procedureVersion: 1`の新しい仮説登録から開始する。

旧記録を新しい対処の起点に再利用する場合も、旧EVを書き換えて昇格させない。
新しい`RC-xxxxx`を作成し、起点評価として旧EVを参照する。

## サブエージェントの分担

1. 横展開担当は、同じ直接原因の類似箇所をソース中心に列挙する。
2. 仮説担当は、この文書を読んで`RC-xxxxx`の初案を報告する。
3. レビュー担当は、仮説担当とは別に補足・反証・代替仮説を報告する。
4. rootは証拠を照合し、確定または追加レビューを判断する。
5. 確定後だけ、実装担当へ`ROOT-xxxxx`の範囲と受入条件を渡す。

各担当は追跡ファイルを直接変更せず報告だけを返す。rootが記録を更新することで、
同時編集と、分析担当が自説を自分で確定することを防ぐ。
